# Deployment guide

Nothing is deployed automatically. This guide prepares a production deployment; follow the
checklists before exposing the application.

## Hosting options

Requirements: a container runtime (or Node 22), PostgreSQL 17, **persistent disk for evidence files**
(the only storage driver today is local disk), HTTPS, environment variables and log collection.

| Option | Fit | Notes |
| --- | --- | --- |
| **Single VM + Docker Compose** (any cloud VPS) | ✅ Best fit today | Uses the provided `docker-compose.yml` as is; add a TLS terminator (e.g. Caddy or Traefik) in front of `web:8080`, or a cloud load balancer. Volumes give persistence for PostgreSQL and uploads. |
| **Container PaaS with volumes** (e.g. platforms that offer persistent disks + managed Postgres) | ✅ Works | Deploy `apps/api` and `apps/web` images; attach a persistent volume to the API at `STORAGE_LOCAL_DIR`; run a **single API instance** (in-memory rate limits, local storage). Verify the provider's current volume and HTTPS support. |
| **Kubernetes / ECS with multiple API replicas** | ⚠️ Needs work | Requires an S3-compatible `StorageProvider` and a shared rate-limit store before scaling out. |
| **Static hosting for the SPA + separate API domain** | ⚠️ Not recommended | Cross-site cookies would need `SameSite=None` and CSRF review; keep SPA and API on the same origin (nginx proxy). |

## Production configuration

`NODE_ENV=production` makes the API refuse to start unless `COOKIE_SECURE=true` and `APP_URL` /
`WEB_ORIGIN` are explicitly set.

```bash
cp .env.docker.example .env.docker
# Set strong unique values (e.g. `openssl rand -base64 32`) for POSTGRES_PASSWORD and APP_DB_PASSWORD,
# WEB_ORIGIN / APP_URL to your public https URL, REGISTRATION_ENABLED=false for private instances.
docker compose --env-file .env.docker up -d --build --wait
```

- **CORS & cookies:** SPA and API share one origin through nginx; `WEB_ORIGIN` must list exactly that
  origin. Cookies are `HttpOnly; SameSite=Lax; Secure`. Terminate TLS in front of nginx and keep
  `TRUST_PROXY=true` (one proxy hop) so rate limits see the real client IP; if you add a second proxy
  layer, adjust `trust proxy` accordingly.
- **Secrets:** only in `.env.docker` on the host or in your platform's secret store — never in Git.
- **AI (optional):** `AI_PROVIDER=anthropic`, `ANTHROPIC_API_KEY`, quotas `AI_DAILY_LIMIT_PER_USER/ORG`;
  an org admin must still opt in.

## First administrator

Do not create an account with a shared or published password. With registration disabled:

```bash
docker compose --env-file .env.docker exec api \
  node dist/cli/create-admin.js --email admin@company.com --name "Admin Name" --org "Company"
# prints a one-time generated password; or pass ADMIN_PASSWORD via -e to choose it
```

The admin then signs in, changes the password (*Settings*), and adds members.

## Database migrations

- Migrations are versioned in `apps/api/prisma/migrations` and applied automatically at API start
  (`prisma migrate deploy`, schema-owner role). Never run `migrate dev` or `migrate reset` in production.
- Write **expand/contract** migrations: add columns/tables first (backward compatible), deploy code,
  then remove old structures in a later release. This keeps rollback possible.
- Manual run: `docker compose exec api sh -c 'DATABASE_URL="$MIGRATE_DATABASE_URL" ./node_modules/.bin/prisma migrate deploy'`.

## Backups

- **Database:** daily logical backups with retention, e.g.
  `docker compose exec -T db pg_dump -U qtm_owner -d qtm -Fc > qtm-$(date +%F).dump`,
  copied off the host (encrypted). Managed PostgreSQL: enable point-in-time recovery.
- **Evidence files:** back up the `uploads` volume (e.g. `docker run --rm -v <project>_uploads:/data -v $PWD:/backup alpine tar czf /backup/uploads-$(date +%F).tgz -C /data .`).
- **Test the restore** regularly: `pg_restore -d <empty db> qtm-YYYY-MM-DD.dump` on a staging host.

## Rollback

1. Keep the previous image tags (`qtm-api:<sha>`, `qtm-web:<sha>`).
2. If a release fails after a backward-compatible (expand) migration: redeploy the previous tags — the
   schema still works with old code.
3. If a migration was destructive or incompatible: stop the API, restore the pre-deploy database
   backup, redeploy the previous tags. This is why destructive changes must ship separately.
4. Verify with `GET /api/health/ready` and the smoke checks in `scripts/compose-smoke.sh`.

## Observability

- Structured JSON logs (Pino) to stdout with `X-Request-Id` correlation (generated by nginx, propagated
  to the API, returned on every response and included in 500 error bodies). Cookies, authorization
  headers and CSRF tokens are redacted; request bodies (passwords, AI prompts, reports) are never logged.
- Health: `/api/health/live` (process up) and `/api/health/ready` (database reachable; 503 otherwise).
- Request duration and status are logged per request by `pino-http` — usable for log-based metrics
  (latency percentiles, error rates) in your log platform. A Prometheus endpoint is not included.

## Go-live checklist

- [ ] HTTPS in front of nginx; HTTP redirects to HTTPS
- [ ] `NODE_ENV=production`, `COOKIE_SECURE=true`, `APP_URL`/`WEB_ORIGIN` = public URL
- [ ] Strong, unique `POSTGRES_PASSWORD` and `APP_DB_PASSWORD`; `.env.docker` readable only by the deploy user
- [ ] `REGISTRATION_ENABLED` decided (false for private instances); first admin created with the CLI
- [ ] Persistent volumes for PostgreSQL and uploads; backups scheduled **and a restore tested**
- [ ] Log collection and alerting on 5xx rate and `/api/health/ready`
- [ ] CI green on the deployed commit (including the Compose smoke test)

## Security checklist (production)

- [ ] Password reset requires a mail provider — until one is integrated, reset links are **not delivered**; communicate this or disable the flow
- [ ] Decide on malware scanning (no engine bundled; files are marked “not scanned”)
- [ ] Single API instance (in-memory rate limits) or add a shared rate-limit store
- [ ] Database port not exposed publicly (compose keeps it on the internal network)
- [ ] AI disabled unless the vendor's data terms are accepted; quotas set
- [ ] Review `docs/SECURITY.md` known gaps

## Readiness verdict

The application is **ready for a controlled pilot** (single instance, trusted users, HTTPS, backups).
It is **not yet ready for open public production** because password-reset e-mail delivery is missing
(a user who forgets their password has no self-service recovery, and there is no admin password-reset feature yet) and uploads are not malware-scanned.
